PiDeck / feature feasibility

「小问题」状态

目标：A 会话需要主人回答时，主人在 B 会话工作也能从侧栏发现；不弹全局窗口，不打断当前工作。

调查结果：可行 预计风险：低～中 当前：仅调查，未改 src

结论

值得做。最稳的方案不是新增后端 Agent 状态，而是把现有的待回答提问请求派生为侧栏展示状态：有请求时显示「小问题」，点回该会话后继续使用现有提问框。

A 发起提问→ extension_ui_request 留在全局状态→ B 工作时 A 显示「小问题」→ 点击 A，现有提问框出现

现有代码已经具备的基础

  • 主进程已有 extension_ui_request，支持 select、confirm、input、editor。
  • 渲染层已有全局 activeUiRequest，请求带有 agentId。
  • 当前提问框只过滤当前 activeAgentId，所以切到 B 后 A 的框会隐藏，但请求本身没有丢。
  • 侧栏已有状态徽章、未读点和会话切换逻辑。

推荐交互

  • A 正在等待回答：状态从「正在思考」替换为「小问题」。
  • 点击 A：恢复现有 modal / ask 卡片，不新增第二套回答逻辑。
  • 提交或取消后：请求收到 completed，状态自动恢复。
  • 多个会话同时提问：每个会话独立显示「小问题」。

预计改动范围

位置改动判断
App.tsx从 activeUiRequest 派生 pendingQuestionAgentIds，侧栏按 Agent 判断是否显示「小问题」。核心不改 IPC
i18n.ts增加 app.statusQuestion 的中文、英文和伪翻译文案。必要遵守多语言规范
styles.css增加 status-question 样式；建议使用信息色或警示色，但不做持续闪烁。轻量避免打扰
后端 / AgentStatus第一版不新增枚举，不让宠物、状态机、运行时逻辑误把提问当成新生命周期状态。建议保持不动

为什么不建议全局提醒

  • 提问不是错误，也不一定需要马上打断主人。
  • 系统通知可能受系统设置、托盘模式和权限影响。
  • 侧栏状态是“可见但不打扰”，和多会话工作流更匹配。
  • 已有的“会话完成未读绿点”可以继续保留，和「小问题」职责不同。

需要留意的边界

  • 同一 Agent 若同时积累多个问题，侧栏只需显示一个「小问题」；切回后按现有顺序处理。
  • 应用重启后，当前前端不会自动恢复未完成的 UI 请求；这是现有机制的边界，第一版可不扩大范围。
  • 提问状态应优先于「正在思考」，但不覆盖「失败」或「启动中」等真正生命周期异常。
  • 要补一个纯函数测试，验证请求完成、取消、切换 Agent 后的状态判断。

推荐实现顺序

先做最小版本：派生状态 → 侧栏显示「小问题」→ 点击恢复现有提问框 → 补 i18n、样式和测试。暂不加入声音、系统通知、闪烁标题或后端新状态。

这条路线改动集中在 renderer，能解决“人在 B 会话却不知道 A 在等回答”的核心问题，也不会把 Agent 状态机搞复杂。
